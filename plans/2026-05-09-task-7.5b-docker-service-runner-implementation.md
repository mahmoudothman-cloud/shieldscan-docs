# Task 7.5b DockerServiceRunner — Implementation Plan

> **For Claude:** This plan follows the Task 7.5a + Task 7.2 phased implementation precedent (Phase 0 verification → Phase 1 framework primitives → Phase 2 lifecycle integration → Phase 3 testing infrastructure → Phase 4 atomic commit). Single atomic commit at Phase 4 covers all phases. Deviation discipline + phase-by-phase instructions under the project's standing rule (everything done in code/server in one self-contained Copy-Paste Reply paragraph per phase).

**Goal:** Ship DockerServiceRunner — the M7 framework for HTTP-API-shaped Docker tools (ZAP + MobSF + future similar). Validates the framework before Task 7.3 (ZAP) and Task 7.4 (MobSF) consumers depend on it.

**Architecture:** Per design doc `plans/2026-05-09-task-7.5b-docker-service-runner-design.md` (commit 8bafa6b). Mid-scope abstraction (Q1 lock); HTTP endpoint poll readiness (Q2); custom shieldscan HTTP client built on net/http stdlib (Q3); polling primitive with exponential backoff (Q4); warm pool with strict reset cleanup + opt-out ephemeral (Q5); readiness probe at spin-up only (Q6); bridge networking with dynamic port mapping bound to 127.0.0.1 (Q7); typed auth helpers + AuthFunc escape hatch (Q8); per-tool MaxSize override + digest-pinning per consumer + HealthCheck nil v1 (Q9).

**Tech Stack:** Go 1.26.2; Docker SDK v28.5.2+incompatible (already imported via Task 7.5a f5d77c8); zerolog; net/http stdlib; testify v1.11.1; existing WarmPool primitive at `internal/tools/docker/`.

## Phase 0 — Verification (READ-ONLY; ~45min; NO COMMIT)

Surface ground-truth state of shieldscan-engine framework boundaries + ZAP/MobSF cleanup contract reality before Phase 1+ design. The design doc §3.5 enumerates verification items; this phase grounds those assumptions in actual repo + tool reality.

### Verification Items

**V1: Framework boundaries.**
- File: `internal/tools/docker/` (shieldscan-engine)
- Surface: exported types from Task 7.5a; package-internal types; whether `docker.Container`, `docker.WarmPool`, `docker.Config` are exported correctly for cross-package use; whether `internal/tools/docker/service/` subpackage location is sensible (vs `internal/tools/dockerservice/` vs other)
- Implication: DockerServiceRunner package location + import surface decisions

**V2: WarmPool primitive reuse.**
- File: `internal/tools/docker/warmpool.go`
- Surface: exact `Cleanup` signature (Task 7.5a Phase 1 used `(ctx, *Container) error`; DockerServiceRunner needs `(ctx, container, baseURL)` shape — verify whether adapter wrapping needed); HealthCheck field nil-safety; spinUp extension point (does WarmPool expose hook for custom spinUp logic OR does DockerServiceRunner need its own spinUp wrapping pool's spinUp)

**V3: Docker SDK port-mapping patterns.**
- File: `internal/tools/docker/container.go` OR wherever container creation happens
- Surface: existing PortBindings configuration patterns (Task 7.5a's Nmap doesn't expose ports; verify whether port-mapping logic is Phase 0 net-new OR existing pattern); ContainerInspect usage for port discovery

**V4: ZAP cleanup contract — `newSession` completeness (SECURITY-CONSEQUENTIAL).**
- Read ZAP API documentation: https://www.zaproxy.org/docs/api/ + https://github.com/zaproxy/zap-api-docs
- Specifically verify:
  - Does `/JSON/core/action/newSession/` reset ALL of: spider history, ascan history, alert list, target context, scope config, authenticated session, user contexts, attack policies, add-on plugin state?
  - What's the API response if `newSession` is called while a scan is in-progress (vs cleanly stopped)?
  - Idempotency: can `newSession` be called multiple times safely?
  - Failure modes: what does `newSession` return on auth failure, service-unavailable, timeout?
- **CRITICAL:** if V4 surfaces "cleanup contract is incomplete" findings (e.g., add-on plugins maintain state across newSession), surface as security concern requiring pause-for-direction. Do NOT proceed to Phase 1 if V4 findings indicate cleanup gaps; consumer-side cleanup hook needs additional steps OR EphemeralContainer becomes default.

**V5: MobSF cleanup contract — `delete_scan` + filesystem cleanup completeness (SECURITY-CONSEQUENTIAL).**
- Read MobSF API documentation: https://github.com/MobSF/Mobile-Security-Framework-MobSF/wiki/3.-REST-API-Endpoints
- Specifically verify:
  - Does `/api/v1/delete_scan` remove uploaded APK/IPA + analysis state + scan metadata + filesystem artifacts?
  - Partial-upload edge case: upload started, scan never created — does cleanup handle?
  - Shared-database tables persisting across scans?
  - Idempotency + failure modes (same shape as V4)
- **CRITICAL:** same V4 stop-if-broken gate applies.

**V6: Image digest resolution.**
- Run: `docker pull ghcr.io/zaproxy/zaproxy:stable; docker inspect ghcr.io/zaproxy/zaproxy:stable -f '{{.Id}}'; docker manifest inspect ghcr.io/zaproxy/zaproxy:stable | grep architecture`
- Surface: SHA256 digest; multi-arch confirmation (amd64 + arm64); image size
- Repeat for `opensecurity/mobile-security-framework-mobsf:latest`

**V7: Worker registry pattern compatibility.**
- File: `cmd/worker/docker_wiring.go` (per Task 7.2 D4 lock)
- Surface: `buildDockerRegistry` function structure; whether it generalizes to DockerServiceRunner consumers OR needs `buildDockerServiceRegistry` parallel function
- Verify: does Pool shutdown lifecycle in `run.go` drain path (Task 7.2 Phase 3 pattern) extend to ServiceRunner pools cleanly?

**V8: Existing HTTP client patterns.**
- Run: `grep -rn "net/http" --include="*.go" internal/ | head -20`
- Surface: existing net/http usage in M5/M6 native tool code; default timeouts; retry patterns; whether framework HTTP client matches existing conventions OR establishes new pattern

**V9: ScanConfig extension surface.**
- File: `internal/tools/runner.go` (per Task 7.2 V2 finding)
- Surface: whether existing flat ScanConfig struct accommodates DockerServiceRunner consumers; specifically whether any consumer-controllable settings need top-level field additions vs ExtraArgs delegation

**V10: net/http defaults sanity check.**
- Stdlib reading: confirm `http.Client` default timeout is 0 (infinite); confirm Transport defaults; confirm `context.Context` cancellation propagation through `Do()`
- Implication: framework's default RequestTimeout 30s + per-request ctx cancellation is the correct shape

### Phase 0 Surface Report Format

After all 10 verification items run, surface findings in structured format:
- Each item V1-V10 with concrete answer or "MISSING / UNCLEAR / SURFACED FOR DIRECTION"
- Specifically flag any architectural deviations requiring pause (V4 + V5 cleanup gaps especially)
- Note any pre-existing patterns that affect Phase 1+ design
- Surface resolved digests from V6 for Phase 1 image-pin commit

**V4/V5 STOP GATE:** If V4 or V5 verdict is anything other than COMPLETE (covers all reset surfaces; idempotent; clear failure modes), surface findings + STOP. Phase 1 cannot begin until cleanup contract gaps are resolved (either consumer-side multi-step cleanup OR EphemeralContainer-as-default policy).

**PAUSE AFTER PHASE 0.** Implementation plan adapts to verified state before Phase 1 begins.

## Discipline Pattern Carry-Forward

The verify-then-adapt-then-document discipline established by Task 7.5a + Task 7.2 carries forward. Anticipated deviation surfaces:

- Phase 0 V1-V10 will surface 1-3 factual deviations (framework signature shapes; net/http convention drifts; existing pattern compatibilities)
- Phase 1 HTTP client + polling primitive may surface edge cases (URL escaping; query parameter encoding; JSON body marshaling defaults; context cancellation propagation through retry loops)
- Phase 2 lifecycle integration will likely surface adaptations to actual WarmPool spinUp extension points

Pre-implementation guidance is unreliable specifically because edge-case interleavings + framework-symmetry concerns surface during implementation; the discipline pattern catches them transparently. Phase 4 commit message footnote enumerates deviations explicitly.

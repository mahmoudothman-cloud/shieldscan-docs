## 1. Executive Summary

Task 7.5b ships **DockerServiceRunner** — the M7 framework for HTTP-API-shaped Docker tools. Distinct from DockerRunner (Task 7.5a, exec-shaped tools like Nmap) by handling long-running service containers that expose REST APIs rather than one-shot CLI invocations. Two consumer tasks depend on this framework: Task 7.3 (ZAP) and Task 7.4 (MobSF).

The framework provides **mid-scope abstraction** per Q1 lock: container lifecycle + HTTP service readiness probing + custom shieldscan HTTP client built on `net/http` stdlib + polling primitive with exponential backoff. Consumer-specific concerns (scan-job creation/poll/fetch shape; result parsing; auth token sourcing) remain consumer-side.

Container lifecycle uses warm pool with strict reset cleanup per Q5 lock — `cfg.EphemeralContainer` flag provides opt-out for high-security scenarios where shared infrastructure isn't acceptable. **Cleanup-leaves-ready-state assumption** (Q6 lock) means readiness probe runs only at pool spin-up; cleanup hooks must restore service to ready state via tool-specific reset API call (ZAP `newSession`; MobSF `delete_scan`). Cleanup correctness is **security-relevant** — incorrect cleanup risks cross-tenant data leakage.

Network configuration uses bridge networking with **dynamic port mapping bound to 127.0.0.1** per Q7 lock — multi-container-safe by construction; localhost-only binding is defense-in-depth complementing future Layer 4 hardening tasks.

Authentication delegates to consumer via `AuthFunc` field with framework-provided typed helpers (`WithAPIKeyHeader`, `WithBearerToken`) per Q8 lock.

## 2. Locked Decisions (Brainstorming Outcome)

| # | Question | Lock | Rationale |
|---|---|---|---|
| Q1 | Framework scope | Mid-scope: lifecycle + readiness + HTTP client + polling primitives | Symmetric to DockerRunner; consumer flexibility for ZAP+MobSF interaction-shape divergence |
| Q2 | Readiness check | HTTP endpoint poll with consumer-specified endpoint | Verifies actual API contract; no dependency on image HEALTHCHECK variance |
| Q3 | HTTP client adapter | Custom shieldscan client built on `net/http` stdlib | Framework-symmetric with DockerRunner pattern; bespoke primitives over stdlib substrate |
| Q4 | Polling primitive | Exponential backoff + max-attempts AND max-duration + tri-state predicate | Adaptive efficiency; defensive belt-and-suspenders termination; sufficient predicate expressiveness |
| Q5 | Warm pool semantics | Pool + strict reset cleanup + opt-out ephemeral (`cfg.EphemeralContainer`) | Startup cost amortized; opt-out for high-security; cleanup-failure-replaces-container preserved |
| Q6 | Container lifecycle | Readiness probe at spin-up only; trust cleanup-leaves-ready-state | Cleanup-then-ready well-defined for ZAP+MobSF; readiness as one-time startup concern |
| Q7 | Network configuration | Bridge networking with dynamic port mapping bound to 127.0.0.1 | Multi-container-safe; deployment-flexible; defense-in-depth via localhost-only |
| Q8 | Authentication delegation | Typed helpers + `AuthFunc` escape hatch | Common cases ergonomic; novel auth preserved; minimal complexity cost |
| Q9 | Closeout bundle | Per-tool MaxSize override + digest-pinning per consumer + no edge-case features + HealthCheck nil v1 | Framework defaults; YAGNI; additive migration paths preserved |

## 3. Architecture

### 3.1 Framework Package Location

`internal/tools/docker/service/` subpackage in shieldscan-engine. Symmetric with `internal/tools/docker/` (Task 7.5a DockerRunner framework) but separate from it because the abstractions diverge enough to warrant separate packages. Shared dependencies (warm pool primitive, container lifecycle helpers from Task 7.5a) imported as needed.

Subject to Phase 0 verification — actual location may be `internal/tools/docker/service/` OR `internal/tools/dockerservice/` OR another structure depending on how Task 7.5a's framework boundaries are organized.

### 3.2 Type Definitions

```go
package service

import (
    "context"
    "net/http"
    "time"

    "github.com/odyssey/shieldscan-engine/internal/events"
    "github.com/odyssey/shieldscan-engine/internal/tools"
    "github.com/odyssey/shieldscan-engine/internal/tools/docker"
    "github.com/rs/zerolog"
)

type ServiceConfig struct {
    Image                  string        // digest-pinned per Q9 + ADR-006 risk #14
    ContainerPort          int           // HTTP service port inside container, e.g., 8080 for ZAP
    EphemeralContainer     bool          // Q5 opt-out: bypass warm pool; create fresh container per scan
    MaxPoolSize            int           // Q9 per-tool override; 0 = framework default 4
    ReadinessEndpoint      string        // e.g., "/JSON/core/view/version/" for ZAP
    ReadinessExpectedStatus int          // default 200
    ReadinessTimeout       time.Duration // default 120s
    ReadinessPollInterval  time.Duration // default 2s
    AuthFunc               func(*http.Request) // typed helpers OR custom closure per Q8
    RequestTimeout         time.Duration // per-request HTTP timeout; default 30s
    CleanupFunc            func(ctx context.Context, container *docker.Container, baseURL string) error
    // CleanupFunc: strict reset; uses detached context per DEVELOPMENT-PATTERNS entry #5
}

type PollOpts struct {
    InitialInterval time.Duration                         // default 1s
    MaxInterval     time.Duration                         // default 30s
    BackoffFactor   float64                               // default 2.0
    MaxAttempts     int                                   // default 1000
    MaxDuration     time.Duration                         // default = ServiceConfig.ScanTimeout (verify in Phase 0)
    BackoffFunc     func(attempt int) time.Duration       // optional override; nil = exponential
}

type PollPredicate func(response []byte) (done bool, err error)

type AuthFunc func(*http.Request)

type Client struct {
    BaseURL    string
    HTTPClient *http.Client
    AuthFunc   AuthFunc
    Log        zerolog.Logger
}

// Methods: Get(ctx, path, dest), Post(ctx, path, body, dest), PollUntil(ctx, path, predicate, opts)

type HTTPError struct {
    StatusCode int
    Body       []byte
    Retryable  bool
}

// Auth helpers
// WithAPIKeyHeader(headerName, value string) AuthFunc
// WithBearerToken(token string) AuthFunc

type DockerServiceRunner struct {
    ToolName      string
    ToolCategory  string
    Pool          *docker.WarmPool
    ServiceConfig ServiceConfig
    BuildScan     func(target tools.Target, cfg tools.ScanConfig, client *Client) ([]events.RawFinding, error)
    Log           zerolog.Logger
}
```

`BuildScan` is consumer-defined; receives target + scan config + framework HTTP client; returns RawFindings or error. The framework provides `Client` + container lifecycle; consumer drives the scan logic (create job → `PollUntil` status → fetch results → parse to RawFindings).

### 3.3 Lifecycle Flow

```
Worker receives scan job
    ↓
DockerServiceRunner.Run(ctx, target, cfg)
    ↓
Pool.Checkout(ctx)  [or fresh-container path if cfg.EphemeralContainer]
    ↓ cache miss → spinUp:
        ContainerCreate with PortBindings: {ContainerPort/tcp: [{HostIP: "127.0.0.1", HostPort: ""}]}
        ContainerStart
        ContainerInspect → discover dynamic host port
        Construct BaseURL = "http://127.0.0.1:<dynamic-port>"
        waitForReady(ctx, BaseURL+ReadinessEndpoint, ReadinessTimeout)
        Mark available
    ↓
Construct Client{BaseURL, HTTPClient, AuthFunc, Log}
    ↓
Consumer's BuildScan(target, cfg, client)
    [typically: client.Post to create scan → client.PollUntil for status →
     client.Get for results → parse to RawFindings]
    ↓
Pool.Return(ctx, container) via defer
    [CleanupFunc with context.WithoutCancel(ctx) + 30s timeout per
     DEVELOPMENT-PATTERNS entry #5; on success: container returned to pool;
     on failure: container stopped + replaced]
    ↓
Findings flow to ADR-017 inline pipeline → ADR-025 ingest consumer
```

### 3.4 Cleanup Hook Contract

CleanupFunc is security-relevant. Failure leaves cross-tenant data leakage risk.

```go
// Example for ZAP (consumer-side):
func zapCleanup(ctx context.Context, container *docker.Container, baseURL string) error {
    cleanupCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 30*time.Second)
    defer cancel()

    cleanupClient := &http.Client{Timeout: 30 * time.Second}
    req, err := http.NewRequestWithContext(cleanupCtx, "GET", baseURL+"/JSON/core/action/newSession/", nil)
    if err != nil {
        return fmt.Errorf("zap cleanup: build request: %w", err)
    }
    // Inject auth (consumer has access to its own AuthFunc)
    cfg.AuthFunc(req)

    resp, err := cleanupClient.Do(req)
    if err != nil {
        return fmt.Errorf("zap cleanup: request failed: %w", err)
    }
    defer resp.Body.Close()

    if resp.StatusCode != http.StatusOK {
        return fmt.Errorf("zap cleanup: non-200 status: %d", resp.StatusCode)
    }
    return nil
}
```

DEVELOPMENT-PATTERNS entry #5 (cleanup-uses-detached-context) applies — `context.WithoutCancel(ctx) + 30s` for in-scope cleanup.

### 3.5 Phase 0 Verification Items

Phase 0 must surface (read-only verification before Phase 1 design):

**V1: Task 7.5a framework boundaries.** Where exactly does `internal/tools/docker/` live; what's exported; what's package-internal. Determines DockerServiceRunner package location + import surface.

**V2: WarmPool primitive reuse.** Verify Task 7.5a's WarmPool primitive supports the lifecycle DockerServiceRunner needs. Specifically:
- `Cleanup func(ctx, *Container) error` signature — DockerServiceRunner needs CleanupFunc with `(ctx, container, baseURL)` shape; verify whether WarmPool's signature accepts arbitrary cleanup OR needs framework adapter
- HealthCheck field — confirm nil-safe per Q9 lock
- Spin-up readiness integration — Q6 lock places readiness in spinUp flow; verify WarmPool exposes spin-up extension point OR DockerServiceRunner wraps with its own spinUp

**V3: Docker SDK port-mapping patterns.** Verify Task 7.5a's container creation patterns include PortBindings configuration. If not (DockerRunner doesn't expose ports for Nmap), DockerServiceRunner adds port-mapping logic.

**V4: ZAP cleanup contract — `newSession` completeness.**
- Does `/JSON/core/action/newSession/` reset ALL of: spider history, ascan history, alert list, target context, scope config, authenticated session, user contexts, attack policies, add-on plugin state?
- What's the API response if `newSession` is called while a scan is in-progress (vs cleanly stopped)?
- Idempotency: can `newSession` be called multiple times safely?
- Failure modes: what does `newSession` return on auth failure, service-unavailable, timeout?
- Surface findings BEFORE Phase 1; if cleanup contract is incomplete, design must adapt.

**V5: MobSF cleanup contract — `delete_scan` + filesystem cleanup completeness.**
- Does `/api/v1/delete_scan` remove uploaded APK/IPA + analysis state + scan metadata + filesystem artifacts?
- Partial-upload edge case: upload started, scan never created — does cleanup handle?
- Shared-database tables persisting across scans?
- Idempotency + failure modes (same as V4).

**V6: Image digest resolution for ZAP + MobSF.**
- ZAP image: `ghcr.io/zaproxy/zaproxy:stable` digest resolution.
- MobSF image: `opensecurity/mobile-security-framework-mobsf:latest` digest resolution.
- Multi-arch verification (amd64 + arm64 for Mahmoud's M4 dev environment).
- Image size confirmation.

**V7: Worker registry pattern compatibility.** Verify `buildDockerRegistry` pattern (from Task 7.2 D4 lock) extends naturally to DockerServiceRunner consumers OR needs `buildDockerServiceRegistry` parallel function.

**V8: Existing HTTP client patterns in shieldscan-engine.** Are there existing net/http usage patterns in M5/M6 native tool code? Determines whether framework HTTP client matches existing conventions OR establishes new pattern.

**V9: ScanConfig extension surface.** Does the existing flat ScanConfig struct (per Task 7.2 V2) need additions for DockerServiceRunner consumers? Specifically: any consumer-controllable settings beyond what ZAP/MobSF expose internally?

**V10: net/http defaults sanity check.** Default `http.Client` has zero timeout (infinite); DockerServiceRunner Client must provide explicit timeouts. Verify the framework's defaults align with project's existing HTTP timeout conventions.

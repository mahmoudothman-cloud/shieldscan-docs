## 4. Verification Methodology

Per Task 7.5c V4 §4 precedent: 6-step per-surface cycle for each S1-S7 surface:

1. **Baseline** — capture pre-state (surface should be empty or known initial state)
2. **Populate** — create state (testbed APK upload + scan for S1-S3; synthetic state injection via discovered API for S4-S7)
3. **Verify-present** — confirm populated state via inspect method (docker exec + sqlite/filesystem for S1-S3; REST API for S4-S7)
4. **Cleanup-call** — invoke POST `/api/v1/delete_scan` with hash parameter
5. **Verify-reset** — re-inspect via same method as step 3; capture post-state
6. **Record verdict** — RESET_COMPLETE / PARTIAL_RESET / NOT_RESET / FAILED_TO_VERIFY per §7 framework

**Inspection method per surface category** (per Q3-(α) refinement): S1-S3 source-code-known surfaces use container-internal access (docker exec + sqlite3 against MobSF `db.sqlite3` + filesystem `ls`); S4-S7 V5-UNCLEAR surfaces use REST API only (FAILED_TO_VERIFY for absent APIs as honest architectural finding).

### 11.6 Architectural Insight Documentation (Two Independent Findings)

**Finding F1 — Configuration-State Cleanup Architectural Boundary (S4 + S5-S7):** MobSF v4.4.6 `delete_scan` cleanup contract is fundamentally hash-scoped (per-scan); configuration-scoped state (suppression registry + user accounts + instance settings + plugin tuning) is structurally outside `delete_scan`'s authority. (a) S4 schema-locked: `StaticAnalyzer_suppressfindings` primary association is `PACKAGE_NAME` (varchar 260); `delete_scan` operates on MD5 hash; schema design prevents intersection even hypothetically. (b) S5-S7 REST API completeness gap: S5 users have only Django web admin endpoints (non-REST); S6 settings + S7 plugin tuning have no REST representation in v4.4.6. **Finding shape stronger than Task 7.5c V4's ZAP documentation-gap finding** — MobSF's is a schema design choice + REST API completeness gap, not a documentation defect.

**Finding F2 — Sync-Mode `delete_scan` Race Condition Producing Uncleanable Orphan State (IF2 bonus):** Mid-scan `delete_scan` in sync mode (v1 engine default per Task 7.4 Q4 lock) produces partial-cleanup orphan state that `delete_scan` itself cannot remediate. Root cause: source-code `home.py` lines 549-559 guard "scan can only be deleted after it is completed" rejection path on `settings.ASYNC_ANALYSIS=true` AND `EnqueuedTask` row existence; in sync mode neither condition holds; `delete_scan` proceeds and races still-running scan's filesystem mutations. Empirical: HTTP 500 + Errno 39 Directory not empty; RecentScansDB wiped; StaticAnalyzerAndroid row + uploads dir remain as orphans. Recovery path infeasible: follow-up `delete_scan` returns "not found" because RecentScansDB existence-check at home.py:547 short-circuits before touching orphan StaticAnalyzer row + uploads dir. Orphan is `delete_scan`-uncleanable through REST API. **Operational implication for engine consumer:** Same-tenant warm-pool retention path (if ever implemented) requires defensive code handling sync-mode race OR `MOBSF_ASYNC_ANALYSIS=1` mode adoption. Reinforces RETAIN verdict from second independent angle.

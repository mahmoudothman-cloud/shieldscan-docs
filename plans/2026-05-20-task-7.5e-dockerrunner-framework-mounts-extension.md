## 2. Phase 0 v2 Empirical Findings (Major Scope-Simplification)

Phase 0 v2 verification produced 24th cumulative session-tail framing-drift catch via V1 empirical result.

### 2.1 V3 `mount.Mount` API Shape

- **Import:** `github.com/docker/docker/api/types/mount`
- **Docker SDK pin:** `v28.5.2+incompatible` (per `go.mod`)
- **Existing usage:** ZERO (Mounts extension introduces this import package to the codebase)
- **Struct shape:** `mount.Mount{Type, Source, Target, ReadOnly}` where Type ∈ {TypeBind, TypeVolume, TypeTmpfs, …}

### 2.2 V2 Bind-Mount fs-Mode (Baseline Confirmed)

Bind-mount works end-to-end. `/tmp/trivy-fs-test:/scan:ro` produces 57 vulns across 3 manifests (matches Task 7.1 Phase 0 v2 baseline 238,336-byte JSON). Scan duration ~5.98s.

### 2.3 V1 Socket-vs-OCI (CRITICAL SCOPE-SIMPLIFICATION FINDING)

**V1.s-ii LOCKED — OCI-sufficient.** Trivy image-mode pulls `alpine:3.10` from OCI registry without Docker socket access. Both no-socket and with-socket paths produced identical output (1 vuln; 22,827-byte JSON; ~6.5s scan).

**Implication:** Image-mode integration test `t.Skip` rationale was empirically incorrect ("Docker socket mount required" framing); actual gap is fs-mode bind-mount only. **Framework extension scope simplified:** bind-mount support sole essential capability; image-mode requires no framework change.

Task 7.1 `integration_test.go` cited socket as resolution path; empirical reality narrower. 24th framing-drift catch this session-tail.

### 2.4 V4 ReadOnly Semantics

`ReadOnly:true` sufficient for fs-mode scanning. Trivy fs-scan is purely read-only against target tree. Plan recommends `ReadOnly:true` default for Trivy bind-mount (defense-in-depth; tenant-isolation). Identical finding counts vs read-write mount.

## 3. Architectural Decisions (Plan-Level Locks)

### 3.1 Q1 α.ii Closure Capture — Framework Implementation Shape

**Lock:** Config struct extended with `Mounts []mount.Mount` field; WarmPool constructs `DefaultContainerFactory` closure capturing `cfg.Mounts`; `newContainer` signature accepts mounts parameter. `ContainerFactoryFunc` signature unchanged.

**Implementation surface:**

- `internal/tools/docker/warmpool.go` — Config struct + Mounts field; closure construction in `New()` (or analogous factory site)
- `internal/tools/docker/container.go` — `newContainer` signature extension accepting `mounts []mount.Mount`; `HostConfig.Mounts` populated
- `internal/tools/docker/dockerrunner.go` — no direct change (Config-mediated)

### 3.2 Q2.s-ii OCI-Sufficient — Trivy Mounts Configuration

**Lock:** Trivy NewPool passes single bind-mount for fs-mode; no Docker socket mount.

**Mount specification:** `{Type: mount.TypeBind, Source: "<scan-target-path>", Target: "/scan", ReadOnly: true}`

**Path strategy:** Bind-mount source is the scan target path; container target `/scan` is canonical mount point. fs-mode Trivy CLI invocation uses `/scan` target.

**Note:** Single warm-pool serves both image-mode (no mount needed) + fs-mode (uses bind-mount). Image-mode containers ignore unused mount; harmless. Single shared pool per Q2 Task 7.1 lock preserved.

### 3.3 W1 (a) Integration Test `t.Skip` Lift

**Lock:** Both image-mode + fs-mode `t.Skip` removed in this task (Phase D operational close criterion).

- **TestIntegration_TrivyFs_TestData** — `t.Skip` removable AFTER framework extension lands (depends on `Config.Mounts` → bind-mount plumbing)

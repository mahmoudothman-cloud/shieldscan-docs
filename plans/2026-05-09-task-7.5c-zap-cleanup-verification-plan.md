## 1. Purpose

Empirically verify what state surfaces ZAP's `/JSON/core/action/newSession/` API endpoint resets. Phase 0 of Task 7.5b read public ZAP REST API documentation; the documentation only states "Creates a new session, optionally overwriting existing files" — does not enumerate per-surface reset semantics. Without empirical verification, ZAP's `cfg.EphemeralContainer = true` v1 default is the safety-conservative ZAP-runner shape (per Task 7.5b V4 Option γ resolution). Verification informs whether v1 default can flip to `false` (warm pool with strict reset cleanup; restores startup amortization for ZAP's 3.6 GB image).

## 2. Scope (Path A — Plan Only This Session)

**In scope tonight:** Verification plan artifact (this document); methodology design; testbed selection; per-surface population + inspection cycle design; idempotency + failure-mode test design; result evaluation framework.

**Out of scope tonight (forward-pinned to execution session):** Actual testbed spinup; actual ZAP container spinup at pinned digest `sha256:8770b23f9e8b49038f413cb2b10c58c901e5b6717be221a22b1bcab5c9771b8a`; populate-state-call-newSession-observe cycle execution; per-surface verdict; final cumulative verdict + recommendation for ZAP `cfg.EphemeralContainer` default flip.

## 3. Testbed Selection

**Selected:** OWASP juice-shop (https://github.com/juice-shop/juice-shop). Single Docker container; well-known vulnerable surface (XSS, SQLi, broken auth, etc.); HTTP API for assertions; established baseline image.

**Rationale:** ZAP needs a target to spider + active-scan against to populate spider/ascan/alert state. juice-shop is the lowest-friction option: single container; no DB setup; comprehensive vulnerability surface; widely used for ZAP demos (so existing community patterns may inform methodology). DVWA + WebGoat + bWAPP are alternatives; juice-shop preferred for setup simplicity.

**Pinned digest forward-pin:** Verification execution should pin juice-shop image digest as well; otherwise behavior may drift across testbed versions. Plan to capture digest at execution time.

**Setup:** `docker pull bkimminich/juice-shop:latest` at execution time; capture pinned digest; `docker run -p 3000:3000 <pinned-digest>`; testbed listens on `http://localhost:3000`.

## 4. Verification Methodology

Per-surface verification cycle:

1. Establish baseline (call ZAP API to inspect surface state; expect empty/default).
2. Populate state via ZAP API calls against juice-shop testbed.
3. Verify state present (call inspection API; expect populated).
4. Call `/JSON/core/action/newSession/`.
5. Verify state reset (call inspection API; expect empty/default per surface).
6. Record verdict per surface (`RESET_COMPLETE` / `PARTIAL_RESET` / `NOT_RESET` / `FAILED_TO_VERIFY`).

Each surface gets its own cycle; surfaces tested in independent ZAP instance OR sequenced cycles in single instance with `newSession`-between-cycles to ensure clean baseline.

## 5. Per-Surface Verification Design

**Surface 1 — Spider History.** Populate: `/JSON/spider/action/scan/?url=http://localhost:3000`. Wait for completion: `/JSON/spider/view/status/` until 100. Inspect: `/JSON/spider/view/results/?scanId=N`. Expected pre-state: ≥1 result (URLs discovered). Expected post-state: 0 results OR scan no longer exists.

**Surface 2 — Active Scan History.** Populate: `/JSON/ascan/action/scan/?url=http://localhost:3000`. Wait for completion: `/JSON/ascan/view/status/` until 100. Inspect: `/JSON/ascan/view/scans/`. Expected pre-state: ≥1 scan record. Expected post-state: 0 scan records.

**Surface 3 — Alert List.** Populate: implicit via Surface 2 (active scan generates alerts). Inspect: `/JSON/core/view/alerts/`. Expected pre-state: ≥1 alert (juice-shop has many vulnerabilities). Expected post-state: 0 alerts.

**Surface 4 — Target Context.** Populate: `/JSON/context/action/newContext/?contextName=verification-test`. Inspect: `/JSON/context/view/contextList/`. Expected pre-state: contextName in list. Expected post-state: contextName absent OR empty list.

**Surface 5 — Scope Config.** Populate: `/JSON/context/action/includeInContext/?contextName=verification-test&regex=http://localhost:3000.*`. Inspect: `/JSON/context/view/includeRegexs/?contextName=verification-test`. Expected pre-state: regex present. Expected post-state: regex absent OR context no longer exists OR endpoint errors.

**Surface 6 — Authenticated Session Configuration.** Populate: `/JSON/authentication/action/setAuthenticationMethod/?contextId=N&authMethodName=formBasedAuthentication&authMethodConfigParams=...&loginUrl=...&loginRequestData=...` (concrete values per juice-shop login form). Inspect: `/JSON/authentication/view/getAuthenticationMethod/?contextId=N`. Expected pre-state: method = `formBasedAuthentication`. Expected post-state: method = `manualAuthentication` (default) OR context no longer exists.

**Surface 7 — User Contexts.** Populate: `/JSON/users/action/newUser/?contextId=N&name=verification-user`. Inspect: `/JSON/users/view/usersList/?contextId=N`. Expected pre-state: ≥1 user. Expected post-state: 0 users OR context no longer exists.

**Surface 8 — Attack Policies.** Populate: `/JSON/ascan/action/addScanPolicy/?scanPolicyName=verification-policy`. Inspect: `/JSON/ascan/view/scanPolicyNames/`. Expected pre-state: `verification-policy` in list (alongside default policies). Expected post-state: `verification-policy` absent (default policies preserved).

**Surface 9 — Add-on Plugin State.** Populate: `/JSON/ascan/action/setPolicyAttackStrength/?id=NNN&attackStrength=HIGH&scanPolicyName=Default+Policy` (modifies plugin attack strength config). Inspect: `/JSON/ascan/view/policies/?scanPolicyName=Default+Policy`. Expected pre-state: id NNN strength = HIGH. Expected post-state: id NNN strength = MEDIUM (default) OR ZAP entirely re-loads from disk.

**Forward-pin for execution:** All API endpoints cited above are based on ZAP API documentation as of plan-authoring; execution session must verify each endpoint exists + behaves as expected in pinned ZAP version `sha256:8770b...`. If any endpoint differs (renamed; deprecated; replaced), execution session adapts methodology + documents adaptation.

## 6. Idempotency + Failure Mode Tests

**IF1 — Idempotent newSession.** Call `/JSON/core/action/newSession/` on freshly-started ZAP (no state). Expect: HTTP 200 + `{Result: OK}`. Then call `newSession` again. Expect: HTTP 200 + `{Result: OK}`. Verifies `newSession` doesn't error on already-clean state.

**IF2 — newSession during in-progress active scan.** Start `/JSON/ascan/action/scan/`. Verify scan in progress: `/JSON/ascan/view/status/` < 100. Call `/JSON/core/action/newSession/`. Expect: outcome captured (200? error? scan terminated? scan continues?). This is the critical edge case — design doc 3067c92 §3.4 forward-pinned this question.

**IF3 — newSession with insufficient privileges (if applicable).** N/A for ZAP without auth-protected API (default). If verification version requires API key + insufficient-perms is testable, add cycle.

## 7. Result Evaluation Framework

**Per-surface verdict:**

- `RESET_COMPLETE` = pre-state populated + post-state empty/default
- `PARTIAL_RESET` = pre-state populated + post-state non-empty but reduced (e.g., spider results count > 0 but < pre-state count)
- `NOT_RESET` = pre-state populated + post-state == pre-state
- `FAILED_TO_VERIFY` = endpoint errored OR ambiguous result

**Cumulative verdict logic:**

- All 9 surfaces `RESET_COMPLETE` + IF1 idempotent + IF2 acceptable behavior → **RECOMMEND flip** `cfg.EphemeralContainer = true → false` (warm pool with strict cleanup safe).
- Any surface `NOT_RESET` OR `PARTIAL_RESET` → **RECOMMEND retain** `cfg.EphemeralContainer = true` (cleanup contract incomplete).
- `FAILED_TO_VERIFY` surfaces → **RECOMMEND additional verification** before lock.
- IF2 returns "scan continues" or "scan errors with corrupted state" → **RECOMMEND retain** v1 default + document edge case.

## 1. Purpose

Implement Trivy as v1 ShieldScan SAST/SCA + container vulnerability scanner consumer per SPEC §3.2 commitment. Trivy is exec-shape DockerRunner consumer (CLI-shaped tool with single-execution + stdout-output) per ADR-026 framework assignment. v1 scope is two-mode (image + fs) with vuln scanner only; secret/misconfig/license scanners + repo/config/sbom modes forward-pinned to v1.1+ separate tasks.

This task is the 4th DockerRunner consumer in implementation order (Nmap M7.2 → ZAP M7.3 → MobSF M7.4 → Trivy M7.1) but the FIRST exec-shape consumer beyond Nmap precedent. Tests DockerRunner framework abstraction against multi-modal CLI tool integration; ADR-026 line 2093 explicitly anticipates this task may surface framework gaps (output streaming for large outputs; exit-code-leniency edge cases) — additive framework changes pre-authorized.

## 2. v1 Scope (Q1 lock — SPEC-§3.2-literal)

**In-scope (v1):**

- **image mode** (Trivy `trivy image <ref>`) — vulnerability scanning of container images; OS package vulnerabilities + language dependency vulnerabilities within image layers
- **fs mode** (Trivy `trivy fs <path>`) — vulnerability scanning of filesystem path; typically code repository or unpacked application directory
- **Single scanner:** `--scanners vuln` only

**Out-of-scope (forward-pinned to v1.1+):**

- **secret scanner** (any mode) — sensitive credential detection
- **misconfig scanner** (any mode) — IaC misconfiguration detection
- **license scanner** (any mode) — license compliance
- **repo mode** (Git remote fetch) — adds remote-fetch complexity
- **config mode (IaC)** — Terraform/K8s/Dockerfile dedicated misconfiguration scanning
- **sbom mode** (CycloneDX/SPDX consumption) — SBOM-input scanning

Trivy is genuinely multi-modal (image/fs/repo/config/sbom × vuln/secret/misconfig/license). v1 selects the SPEC-§3.2-literal subset that directly fulfills "SCA + container" commitment; remainder forward-pinned for incremental rollout.

## 3. Architectural Decisions

### 3.1 Registration Shape (Q2 lock — TWO ToolRunner instances; same package)

Per ToolRunner.Category() contract (`internal/tools/runner.go`) enumerating "sca" AND "container" as distinct values, Trivy registers as TWO ToolRunner instances:

- **TrivyContainerScanner** — `Name()` "trivy-container"; `Category()` "container"; targets container image references
- **TrivyFsScanner** — `Name()` "trivy-fs"; `Category()` "sca"; targets filesystem paths

Both consumers live in single internal package (`internal/tools/docker/trivy/`) with shared parser + client + types. Two ToolRunner struct types delegate to shared `runTrivy(ctx, target, cfg, mode)` function with internal mode constant (`modeImage` / `modeFs`).

**Rationale:** preserves ToolRunner.Category() semantic accuracy (Trivy genuinely IS both SCA and container scanner; forcing single category loses clarity); clean orchestrator + pricing-tier composition (each mode addressable by distinct `Name()`); shared internal code (minimal duplication); explicit two-consumer registration (clearer than mode-conditional factory pattern).

### 3.2 Container + Framework Shape (Q3 lock)

**Image:** `aquasec/trivy:<version>` pinned digest (specific version verified at Phase 0 v2 / Phase 1 execution time per Task 7.4 V1 convention).

**Framework:** DockerRunner exec-shape (NOT DockerServiceRunner per ADR-026 §"Exec-shape" line 2113); DefaultContainerFactory. Mirrors Nmap exec-shape precedent.

**Vulnerability database (vuln-db):** pre-downloaded volume mount. Trivy downloads ~50MB vuln-db on first run; initial pull at warm-pool first spinup; persists in mounted volume across scans. Forward-pin v1.1+: DB refresh strategy (TTL / on-demand).

**Cache:** warm-pool retained per ADR-026 warm-pool semantics; cache persists until pool eviction. Forward-pin v1.1+: cache size monitoring + bounds.

**Output format:** JSON (`--format json`; Trivy native). Most lossless; well-documented schema; rich for parser. SARIF + CycloneDX deferred to future-task additive outputs.

**Memory bounds:** v1 whole-output buffering (standard stdout pipe to byte buffer); ADR-026 line 2093 escape hatch forward-pinned for streaming if 5000+ findings cause empirical pressure.

**Exit-code:** Trivy CLI default behavior (exit 0 on completion regardless of finding count); no `--exit-code 1` flag passed. Framework strict convention preserved (exit 0 = success); per-consumer exit-code leniency forward-pinned to additive framework change if future use cases require.

### 3.3 Implementation Package Layout (Q4 lock)

Flat structure mirroring Nmap precedent:

```
internal/tools/docker/trivy/
  trivy.go              # TrivyContainerScanner + TrivyFsScanner struct definitions + ToolRunner method implementations
  parser.go             # shared JSON parser; parseTrivyJSON + buildVulnFinding
  parser_test.go        # table-driven parser tests with mode-distinguishing cases
  scan.go               # shared runTrivy + Trivy CLI invocation logic
  scan_test.go          # scan invocation tests with mock docker client
  types.go              # Trivy JSON schema structs (TrivyOutput + TrivyResult + TrivyVulnerability)
  testdata/
    image-scan.json     # representative Trivy image-mode JSON fixture
    fs-scan.json        # representative Trivy fs-mode JSON fixture
    empty.json          # zero-findings fixture
    malformed.json      # error-handling fixture
```

**Rationale:** Mirrors Nmap exec-shape precedent at `internal/tools/docker/nmap/`; explicit two-consumer registration; shared internal functions; standard Go `testdata/` convention.

## 4. Trivy Domain Knowledge

**Trivy CLI invocation shapes:**

- Image mode: `trivy image --format json --scanners vuln <image-ref>`
- Fs mode: `trivy fs --format json --scanners vuln <path>`

**Trivy JSON output schema (essentials):**

- `SchemaVersion: 2` — current; verify at Phase 0 v2
- `ArtifactName: <ref>` — scan target identifier
- `ArtifactType: container_image | filesystem` — drives mode-distinguishing metadata
- `Metadata: {OS, ImageConfig, Layers}` — populated in image mode only
- `Results[]` — uniform array of section results
- Per-result fields: `Target`, `Class` (os-pkgs | lang-pkgs), `Type` (debian | bundler | npm | ...)
- `Vulnerabilities[]` per result with: `VulnerabilityID` (CVE-XXXX-XXXX), `PkgName`, `PkgPath`, `InstalledVersion`, `FixedVersion`, `Severity` (UNKNOWN|LOW|MEDIUM|HIGH|CRITICAL), `CVSSScore` (numeric), `Title`, `Description`, `References[]`, `CweIDs[]`

**Image-mode container scanning specifics:** scans OS packages (apt/yum/apk-installed) + language dependencies (within image layers). Detects vulnerabilities in installed packages by matching against Trivy vuln-db.

**Fs-mode filesystem scanning specifics:** scans dependency manifests in directory tree (Gemfile.lock + package-lock.json + go.sum + requirements.txt + etc.). Detects vulnerabilities in declared/locked dependencies.

**Vuln-db characteristics:** ~50MB compressed; updated daily upstream; sourced from NVD + GitHub Security Advisories + multiple OS-specific advisory databases; bundled DB cached in container per warm-pool architecture.

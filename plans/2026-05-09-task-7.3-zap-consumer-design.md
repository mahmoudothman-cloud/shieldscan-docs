## 1. Executive Summary

Task 7.3 ships ZAP as the first DockerServiceRunner consumer (per Task 7.5b framework; commit 1306ca8). ZAP is a DAST (Dynamic Application Security Testing) tool — runs HTTP-based scans against running web applications; complements Task 7.2's Nmap (network discovery) + future SAST tools. Marks shieldscan's first authenticated-scanning capability and first cross-repo schema extension since Task 7.5b.

Per Task 7.5b V4 lock, ZAP runs in `cfg.EphemeralContainer = true` v1 mode (ZAP `newSession` cleanup contract verification deferred to Task 7.5c). Fresh container per scan; container destroyed at scan end; no cleanup contract risk. Performance tradeoff: 60–120s container startup per scan; acceptable for v1 customer experience; revisitable post-Task-7.5c verification if `newSession` found COMPLETE (would flip to warm-pool + reset cleanup; restore startup amortization).

Two scan modes shipped v1: **Mode B** (Spider + Passive Scan) maps to "Quick" pricing tier (~10–20min wall-clock; predictable passive-scan findings); **Mode C** (Spider + Active Scan) maps to "Full" pricing tier (~30min–2h wall-clock; comprehensive vulnerability findings via ~50+ ZAP active scan rules). **Mode D** (Spider + AJAX + Active) forward-pinned to v2 when SPA customer demand surfaces.

Authenticated scanning v1 ships **cookie pass-through only** — fills SPEC §7.1 wire-schema gap (auth block currently null per ADR-015 forcing function). ScanConfig gains `AuthConfig {Type, Data}` field; v1 supports `Type="cookie"` (orchestrator does login API-side; engine injects cookies via `/JSON/httpSessions/`). Form-based auth + bearer + basic deferred to v2 typed enum migration when (a) Task 7.3 execution surfaces empirical config formats OR (b) 2nd auth-supporting consumer surfaces. ExtraArgs escape hatch (`zap.auth.*` keys) covers form-based power-users v1.

Cross-repo coordination required for Q6 lock: shieldscan-engine `ScanConfig.AuthConfig` field + shieldscan-api Pydantic `AuthConfig` model + SQLAlchemy `ScanJob.auth_config` column (Fernet-encrypted at rest per SPEC §7.1). ADR-015 forcing function status updates from "currently null" to "v1 cookie type enabled; v2 enum expansion pinned."

### 3.2 Type Definitions

Consumer-side types (in `zap` subpackage):

```go
type Config struct {
    APIKey  string
    Mode    ScanMode // ScanModeQuick (Mode B) | ScanModeFull (Mode C)

    SpiderConfig struct {
        MaxDepth    int
        MaxDuration time.Duration
        MaxChildren int
        ThreadCount int
    }

    ActiveScanConfig struct {
        ScanPolicyName string // allowlist-validated
        MaxDuration    time.Duration
    }

    AuthCookies   string            // extracted from ScanConfig.AuthConfig.Data when Type="cookie"
    ExtraArgsAuth map[string]string // zap.auth.* subset when ExtraArgs escape hatch used
}

type ScanMode int
const (
    ScanModeQuick ScanMode = iota // Mode B — Spider + Passive
    ScanModeFull                  // Mode C — Spider + Active
)

func NewBuildScan(cfg Config) func(ctx context.Context, target tools.Target, scanCfg tools.ScanConfig, client *service.Client) ([]events.RawFinding, error)
```

`ScanMode` mapped from `ScanConfig.Depth`: `"quick"` → `ScanModeQuick`; `"standard"` → `ScanModeFull` (with standard params); `"deep"` → `ScanModeFull` (with deep params).

Consumer constructs runner:

```go
runner := &service.DockerServiceRunner{
    ToolName:     "zap",
    ToolCategory: "dast",
    ServiceConfig: service.ServiceConfig{
        Image:              zapImageDigest,
        ContainerPort:      8080,
        EphemeralContainer: true,
        ReadinessEndpoint:  "/JSON/core/view/version/?apikey=" + apiKey,
        ReadinessTimeout:   120 * time.Second,
        AuthFunc:           zapQueryParamAuth(apiKey),
        CleanupFunc:        nil,
    },
    BuildScan: zap.NewBuildScan(cfg),
    Log:       log,
}
```

**Cross-repo type extension** (engine + shieldscan-api):

- `ScanConfig.AuthConfig *AuthConfig` field added on engine side
- `AuthConfig struct {Type string; Data string}` — `Type` = `"cookie"` v1; enum expansion v2; `Data` = cookie string format `"name=value; name2=value2"`
- shieldscan-api Pydantic `AuthConfig` model mirror
- SQLAlchemy `ScanJob.auth_config` Fernet-encrypted column

### 3.3 Lifecycle Flow

```
Worker scan-job
    ↓
DockerServiceRunner.Run(ctx, target, scanCfg)
    ↓
EphemeralContainer = true path:
    ServiceContainerFactory creates fresh ZAP container
    spinUp readiness probe → /JSON/core/view/version/?apikey=<key>
    BaseURL = http://127.0.0.1:<dynamic-port>
    defer container.Stop
    ↓
Construct Client with zapQueryParamAuth AuthFunc
    ↓
BuildScan(ctx, target, scanCfg, client) executes consumer scan logic per Q1–Q9 locks:
    (a) target validation (scheme required; AllowPrivateTargets check)
    (b) auth setup (cookie injection via /JSON/httpSessions/ if AuthConfig.Type="cookie";
        ExtraArgs zap.auth.* path if escape hatch)
    (c) spider scan: POST /JSON/spider/action/scan/ + PollUntil /JSON/spider/view/status/
        via framework Q4 polling
    (d) Mode-B path: wait for passive scan queue drain via /JSON/pscan/view/recordsToScan/
    (e) Mode-C path: also POST /JSON/ascan/action/scan/ + PollUntil /JSON/ascan/view/status/
    (f) bulk fetch alerts via /JSON/core/view/alerts/?baseurl=&start=0&count=5000
    (g) parse alerts → RawFindings per Q8 mapping table
    (h) return findings
    ↓
Container stopped + removed
    ↓
Findings flow to framework enrichment + ADR-017 inline pipeline → ADR-025 ingest
```

| `wascid` | Metadata: `wasc_id` |
| `method` | Metadata: `http_method` |
| `attack` | Metadata: `attack_vector` (also above as Payload) |

- **V16.** Cross-walk ZAP alert IDs ↔ CWE IDs at consumer parser layer.
- **V17.** Verify default policy + 9 built-in policies exact names (Penetration Tester Policy, API Policy, Developer CI/CD, etc.) for ExtraArgs allowlist.

## 7. Brainstorming + Verification Process Acknowledgment

This design followed the per-task brainstorming pattern + Path Y verification rounds. 9 decisions locked across Q1–Q9. Phase 0 verification (read-only doc reads) caught 5 architectural deviations BEFORE Q2 brainstorming locks: V1 docker-compose conflict; V3 AuthConfig gap; V4 pricing tier ≥2 modes; V5 auth-method canonical drift; V8 SPEC §7.1 wire-schema pre-pin (most consequential — reframed Q6 cost asymmetry from β-defensible to γ-cookie-hybrid-correct).

Path Y verification rounds (Q5+Q6+Q7+Q8) each surfaced load-bearing reframes:

- **Q5 verification** grounded ZAP's 9 built-in policies + ~50+ default rules
- **Q6 verification** reframed AuthConfig from "speculative new field" to "fill SPEC §7.1 pre-pinned gap" (saved ~150 LoC speculative form-based implementation)
- **Q7 verification** revealed `?apikey=` canonical (not header — Task 7.5b assumed wrong)
- **Q8 verification** grounded mapping table + `cweid` integer-not-string conversion

**Discipline pattern observation:** Task 7.3 brainstorming + verification surfaced 5 Phase-0 + 4 verification-round deviations = 9 honest disposition decisions before any engine code lands. Pre-implementation guidance failed in different territories (architectural-prose memory; cross-document scope precision; wire-schema pre-commit visibility; canonical-method-vs-undocumented-backward-compat assumption; field-type drift). Verification step at every memory-heavy boundary mitigated.

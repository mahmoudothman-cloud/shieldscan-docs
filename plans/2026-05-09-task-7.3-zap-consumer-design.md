## 1. Executive Summary

Task 7.3 ships ZAP as the first DockerServiceRunner consumer (per Task 7.5b framework; commit 1306ca8). ZAP is a DAST (Dynamic Application Security Testing) tool — runs HTTP-based scans against running web applications; complements Task 7.2's Nmap (network discovery) + future SAST tools. Marks shieldscan's first authenticated-scanning capability and first cross-repo schema extension since Task 7.5b.

Per Task 7.5b V4 lock, ZAP runs in `cfg.EphemeralContainer = true` v1 mode (ZAP `newSession` cleanup contract verification deferred to Task 7.5c). Fresh container per scan; container destroyed at scan end; no cleanup contract risk. Performance tradeoff: 60–120s container startup per scan; acceptable for v1 customer experience; revisitable post-Task-7.5c verification if `newSession` found COMPLETE (would flip to warm-pool + reset cleanup; restore startup amortization).

Two scan modes shipped v1: **Mode B** (Spider + Passive Scan) maps to "Quick" pricing tier (~10–20min wall-clock; predictable passive-scan findings); **Mode C** (Spider + Active Scan) maps to "Full" pricing tier (~30min–2h wall-clock; comprehensive vulnerability findings via ~50+ ZAP active scan rules). **Mode D** (Spider + AJAX + Active) forward-pinned to v2 when SPA customer demand surfaces.

Authenticated scanning v1 ships **cookie pass-through only** — fills SPEC §7.1 wire-schema gap (auth block currently null per ADR-015 forcing function). ScanConfig gains `AuthConfig {Type, Data}` field; v1 supports `Type="cookie"` (orchestrator does login API-side; engine injects cookies via `/JSON/httpSessions/`). Form-based auth + bearer + basic deferred to v2 typed enum migration when (a) Task 7.3 execution surfaces empirical config formats OR (b) 2nd auth-supporting consumer surfaces. ExtraArgs escape hatch (`zap.auth.*` keys) covers form-based power-users v1.

Cross-repo coordination required for Q6 lock: shieldscan-engine `ScanConfig.AuthConfig` field + shieldscan-api Pydantic `AuthConfig` model + SQLAlchemy `ScanJob.auth_config` column (Fernet-encrypted at rest per SPEC §7.1). ADR-015 forcing function status updates from "currently null" to "v1 cookie type enabled; v2 enum expansion pinned."

### 3.2 Type Definitions

Consumer-side types (in `zap` subpackage):

```go
type Config struct {
    APIKey  string
    Mode    ScanMode // ScanModeQuick (Mode B) | ScanModeFull (Mode C)

    SpiderConfig struct {
        MaxDepth    int
        MaxDuration time.Duration
        MaxChildren int
        ThreadCount int
    }

    ActiveScanConfig struct {
        ScanPolicyName string // allowlist-validated
        MaxDuration    time.Duration
    }

    AuthCookies   string            // extracted from ScanConfig.AuthConfig.Data when Type="cookie"
    ExtraArgsAuth map[string]string // zap.auth.* subset when ExtraArgs escape hatch used
}

type ScanMode int
const (
    ScanModeQuick ScanMode = iota // Mode B — Spider + Passive
    ScanModeFull                  // Mode C — Spider + Active
)

func NewBuildScan(cfg Config) func(ctx context.Context, target tools.Target, scanCfg tools.ScanConfig, client *service.Client) ([]events.RawFinding, error)
```

`ScanMode` mapped from `ScanConfig.Depth`: `"quick"` → `ScanModeQuick`; `"standard"` → `ScanModeFull` (with standard params); `"deep"` → `ScanModeFull` (with deep params).

Consumer constructs runner:

```go
runner := &service.DockerServiceRunner{
    ToolName:     "zap",
    ToolCategory: "dast",
    ServiceConfig: service.ServiceConfig{
        Image:              zapImageDigest,
        ContainerPort:      8080,
        EphemeralContainer: true,
        ReadinessEndpoint:  "/JSON/core/view/version/?apikey=" + apiKey,
        ReadinessTimeout:   120 * time.Second,
        AuthFunc:           zapQueryParamAuth(apiKey),
        CleanupFunc:        nil,
    },
    BuildScan: zap.NewBuildScan(cfg),
    Log:       log,
}
```

#### Post-Implementation Note (Phase 5.A revision; per shieldscan-engine commit e905afe)

Phase 1 D1 surfaced `AuthConfig` pre-existed on `tools.Target` struct (line 138 `internal/tools/runner.go`) with 5 typed values (`cookie | bearer | basic | custom_header | form`) plus `Fields map[string]string` for form-auth — pre-dating Task 7.3 brainstorming by months (Task 3.X M3 vintage). Phase 1 disposition: respected existing placement; ZAP consumer reads `target.AuthConfig` (NOT `scanCfg.AuthConfig` per original design doc framing). Phase 2 V2.3 confirmed wire-deserialization happens via `events.JobAuth` (top-level per SPEC §7.1) bridged to `target.AuthConfig` via `processor.jobDispatchToTarget`. Q6 "v2 typed enum migration commitment" framing was redundant — engine already has 5 typed values structurally; ADR-015 forcing function gates runtime activation (orchestrator emits `auth=None` pending decryption + Redis-transit security review).

**Cross-repo type extension** (engine + shieldscan-api):

- `ScanConfig.AuthConfig *AuthConfig` field added on engine side
- `AuthConfig struct {Type string; Data string}` — `Type` = `"cookie"` v1; enum expansion v2; `Data` = cookie string format `"name=value; name2=value2"`
- shieldscan-api Pydantic `AuthConfig` model mirror
- SQLAlchemy `ScanJob.auth_config` Fernet-encrypted column

### 3.3 Lifecycle Flow

```
Worker scan-job
    ↓
DockerServiceRunner.Run(ctx, target, scanCfg)
    ↓
EphemeralContainer = true path:
    ServiceContainerFactory creates fresh ZAP container
    spinUp readiness probe → /JSON/core/view/version/?apikey=<key>
    BaseURL = http://127.0.0.1:<dynamic-port>
    defer container.Stop
    ↓
Construct Client with zapQueryParamAuth AuthFunc
    ↓
BuildScan(ctx, target, scanCfg, client) executes consumer scan logic per Q1–Q9 locks:
    (a) target validation (scheme required; AllowPrivateTargets check)
    (b) auth setup (cookie injection via /JSON/httpSessions/ if AuthConfig.Type="cookie";
        ExtraArgs zap.auth.* path if escape hatch)
    (c) spider scan: POST /JSON/spider/action/scan/ + PollUntil /JSON/spider/view/status/
        via framework Q4 polling
    (d) Mode-B path: wait for passive scan queue drain via /JSON/pscan/view/recordsToScan/
    (e) Mode-C path: also POST /JSON/ascan/action/scan/ + PollUntil /JSON/ascan/view/status/
    (f) bulk fetch alerts via /JSON/core/view/alerts/?baseurl=&start=0&count=5000
    (g) parse alerts → RawFindings per Q8 mapping table
    (h) return findings
    ↓
Container stopped + removed
    ↓
Findings flow to framework enrichment + ADR-017 inline pipeline → ADR-025 ingest
```

### 3.5 Phase 0 Verification Items (post-execution annotations per Phase 5.A revision)

All V-items annotated with surface-report verdicts per shieldscan-engine Phase 0 execution + Phase 1 implementation (commit e905afe):

- **V0** ⚠️ **NEW INFRASTRUCTURE FINDING** (surfaced during Phase 0 execution) — ZAP daemon distinguishes API vs proxy by Host header; with `Host=localhost:<port>`, requests routed to proxy (returns ZAP-error connection-refused); API requires `Host: zap` (or hostname configured via `api.addrs.addr.name=.*`). Phase 1 implication: `zapQueryParamAuth` AuthFunc closure sets `req.Host = "zap"` for all API requests (consumer-local v1 per Phase 5.D 3-instance threshold-gate; framework promotion deferred until 2nd-instance trigger).
- **V1** ✅ **RESOLVED** — pinned ZAP digest `sha256:8770b...` resolves to ZAP v2.17.0 (NOT 2.16.0 per docker-compose pin; Q3 removal makes drift moot); multi-arch confirmed; size 3.6GB.
- **V2** ✅ **RESOLVED** — `-config api.key=<value>` startup flag is primary mechanism; `api.disablekey=false` default; container also requires `-config api.addrs.addr.name=.* -config api.addrs.addr.regex=true` for non-zap-hostname API access.
- **V3** ✅ **RESOLVED** — `X-ZAP-API-Key` header backward-compat WORKS (with `Host: zap`); audit-only finding; doesn't change Q7(B) lock (canonical doc-backed query-param remains v1 method).
- **V4** ✅ **RESOLVED** — Attack Strength enum = `DEFAULT|LOW|MEDIUM|HIGH|INSANE`; Alert Threshold enum = `DEFAULT|OFF|LOW|MEDIUM|HIGH`; pinned for consumer code.
- **V5/V17** ⚠️ **DRIFT** — actual ZAP 2.17.0 ships **22 policies** (NOT 9 per documentation): `"Default Policy"`, `"Pen Test"`, `"API"`, `"API-Minimal"`, `"Sequence"`, `"Dev CICD"`, `"Dev Full"`, `"Dev Standard"`, `"QA CICD"`, `"QA Full"`, `"QA Standard"`, plus 11 `"St-*-Th-*"` strength×threshold combos. Original design doc cited 9 hypothetical names (`"Penetration Tester Policy"`, `"API Policy"`, `"Developer CI/CD Policy"`, etc.) — incorrect. Phase 1 `ascan.go` `zapPolicyAllowlist` hardcodes the 22 actual names.
- **V6** ⚠️ **DRIFT** — `cweid` is JSON STRING (`"693"`), NOT int. Original design doc Q8 mapping table specified `strconv.Itoa(cweid)` conversion; that conversion is unnecessary + would cause Go type error. Phase 1 `parser.go` drops conversion; pass-through directly. Same drift for `wascid`, `pluginId`, `messageId`, `id`.
- **V7** ✅ **RESOLVED-PARTIAL** — `numberOfAlerts` returns count as STRING not int; 12 alerts from 1 brief spider scan; `count=5000` cap not stress-tested but well above plausible Mode B/C scan volume. Pagination upgrade forward-pinned (Q8 Option ii) if execution surfaces alert count >5000.
- **V8** ⚠️ **STOP_GATE_TRIGGERED + RESOLVED** — shieldscan-api Severity enum = `{critical, high, medium, low, info}` all lowercase; ZAP returns capitalized; `parser.go` `mapZAPRisk` normalizes; `"False Positive"` → `drop=true` (V9 intersection). `"Critical"` has no upward mapping (ZAP has no Critical risk).
- **V9** ✅ **RESOLVED** via V8 — drop `"False Positive"` findings at parser layer (Pydantic enum doesn't accept; cannot pass-through).
- **V10** ✅ **RESOLVED** — `evidence` field is single string (ZAP doesn't distinguish request/response); placed into `Metadata['evidence']` (NOT typed `Request`/`Response`); omit when empty.
- **V11** ✅ **RESOLVED** — `solution` placed into `Metadata['solution']` (keep `Description` tight for UI rendering).
- **V12** ⚠️ **DRIFT** — `tags` field is `map[string]string` with URL-valued tag dictionary (NOT list as design doc framing assumed); structured keys: `OWASP_2021_A05`, `CWE-693`, `POLICY_QA_STD`, `SYSTEMIC`, etc. Phase 1 `parser.go` `extractZAPTags` filters `OWASP_*`+`CWE-*` keys; drops `POLICY_*`+`SYSTEMIC` noise; raw tags preserved in `Metadata['tags_raw_json']`.
- **V13** ✅ **STOP_GATE_PASS** — `formBasedAuthentication` `setAuthenticationMethod` accepted `{Result: OK}`; `authMethodConfigParams` format = `loginUrl=<url>&loginRequestData=<url-encoded-form-with-{%username%}-{%password%}-placeholders>`; total ~150–300 chars; well within ExtraArgs escape-hatch capacity; Q6 lock holds.
- **V14** ⚠️ **PARTIAL** — spider accepted `userId=999` (non-existent user) without error (silent-pass); Phase 1 forward-pin: must verify `userId` behavior with valid configured user before relying.
- **V15** 🔮 **FORWARD-PINNED** — session re-auth on logged-out-indicator regex match requires custom logged-in app + auth flow; out of Phase 0 empirical scope; surfaces during Phase 1 ZAP consumer execution against authenticated test target.
- **V16** ✅ **RESOLVED-BETTER-THAN-EXPECTED** — scanner registry pre-carries `cweId`+`wascId` per scanner; alert `cweid` field reliably populated; tags map contains `CWE-NNN` keys redundantly; cross-walk simpler than design doc anticipated.
- **V18** ✅ **RESOLVED** — `/JSON/httpSessions/action/createEmptySession/` + `setSessionTokenValue/` both accept `{Result: OK}`; cookie pass-through path feasible per Q6 cookie-only lock.
